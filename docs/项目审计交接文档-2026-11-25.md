## 1. 项目速览

**定位**：部署在 Cloudflare Pages 上的个人单人自用「数字生活工作台」：成长打卡、待办提醒（微软 To Do 式）、记账账本、家庭药箱、日历（农历/经期）、人际关系档案、随手记（AI 解析）、Web Push 提醒。零构建、无框架、无第三方运行时依赖（仅霞鹜文楷字体按需从 jsDelivr 加载）。

| 层 | 技术 | 位置 |
| --- | --- | --- |
| 前端 | 纯 HTML/CSS/JS 单页应用（index.html ≈1500 行、app.js ≈6000 行、profile.js ≈2200 行、medicine.js ≈820 行、lunar.js 110 行） | `public/` |
| 后端 | Cloudflare Pages Functions（文件即路由，导出 `onRequestGet/Post/Put/Delete`） | `functions/`（约 5500 行） |
| 数据库 | Cloudflare D1（SQLite），16 个迁移 | `migrations/` |
| 对象存储 | Cloudflare R2（联系人附件） | binding `BUCKET` |
| 定时推送 | 独立 Worker，Cron `* * * * *`（每分钟） | `worker/` |
| 安卓壳 | WebView（TWA 式），`com.shuzishenghuo.twa` | `android/` |
| 发版 | `scripts/release.mjs`：版本注入 + 资源内容哈希 + sw.js 生成 + CSP hash 注入 + 语法门禁 | `scripts/` |
| CI | GitHub Actions：语法检查 → 本地从零建库 → 7 个 e2e 测试脚本 → 主题对比度 | `.github/workflows/ci.yml` |

**鉴权模型（理解所有漏洞的前提）**：
- 单管理员。`functions/_middleware.js` 对所有 `/api/*` 校验 HMAC 签名 Cookie `sz_session`（`HttpOnly; SameSite=Lax`，7 天，`functions/api/auth/login.js:85`）；会话带 `sid` 落 `sessions` 表（登出/改密可吊销）。
- 公开接口只有 `/api/auth/login`、`/api/health`、`/api/client-log`；`/api/ext/*` 与 `/mcp` 用 `Bearer szsh_` 令牌 + 按模块 scope（`functions/api/_tokens.js`）。
- 服务端「今天」固定 UTC+8（`functions/_lib.js:100-106` todayStr）；前端 v0.5.48 起改为设备本地时区（两边口径不一致，见 P2-17）。
- 登录失败限流是**单 isolate 内存态**（`login.js:18-40`，15 分钟 10 次），分布式下不精确。
- 管理员密码：PBKDF2-SHA256（10 万次迭代）存 `app_settings.admin_pass_hash`；外部令牌存 sha256。

### 3.2 P1（5 项，建议立即修）

---

#### P1-1 ✅ 安卓发布签名密钥库与口令一并公开在仓库

- **位置**：`android/app/release.keystore`（已入库，`git ls-files` 可见，引入提交 c395007）；`android/app/build.gradle`（signingConfigs 含 `storePassword`/`keyPassword` 配置值）；`android/README.md` 与 `APP_BUILD.md` 在密钥库说明处**直接写出口令**（主审核对原文存在，此处不复述）。
- **影响**：任何拿到仓库的人可以用同一签名密钥构建同包名（`com.shuzishenghuo.twa`）的恶意 APK，对已安装用户做「覆盖升级安装」（同签名同包名允许升级），继承 WebView Cookie/本地数据；APK 发布渠道（GitHub Releases）的用户全部受影响。
- **修复**：① 立即生成新密钥库，改口令，新 keystore 不再入库（加入 `.gitignore`，口令走 `keystore.properties`（ignored）或环境变量）；② 注意：换签名后老用户需**卸载重装**，应发公告并提醒先导出数据；③ 清理 git 历史中的 keystore（`git filter-repo`）+ 让 GitHub support 清缓存，或至少在 README 声明「该密钥已泄露作废，仅历史版本使用」；④ `minifyEnabled false` 建议顺手改为 true。

#### P1-2 ✅ 删除类接口未限定 HTTP 方法：GET 请求即删除（CSRF）

- **位置（共 5 个文件，均为 `export async function onRequest` 且无方法判断、无条件 DELETE）**：
  - `functions/api/events/[id].js:4-11`（删日程）
  - `functions/api/todos/[id]/delete.js:4-10`（删待办）
  - `functions/api/contacts/[id].js:4-11`（**删联系人 + 级联 8 张子表 + 删除其全部 R2 附件**，经 `deleteContactCascade`）
  - `functions/api/profile/delete.js:4-11`（同上）
  - `functions/api/memos/[id].js:3-9`（删随手记）
- **机制**：Pages Functions 的 `onRequest` 对所有 HTTP 方法生效（[官方文档](https://developers.cloudflare.com/pages/functions/api-reference/)）；会话 Cookie 为 `SameSite=Lax`（`login.js:85`），**跨站顶层导航的 GET 会携带 Cookie**（[MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)），中间件只校验 Cookie 不校验方法与 Origin（`_middleware.js:31`）。
- **触发**：已登录用户在任意第三方页面点击链接/被 `location.href` 跳转到 `https://<站点>/api/contacts/3` → 联系人 3 连同档案与附件被删；ID 为自增小整数，可枚举。系统无回收站，不可恢复。
- **修复**：① 5 个文件只导出 `onRequestDelete`（正确范式见 `functions/api/transactions/[id].js:7-11`）；② 纵深防御：`_middleware.js` 对非 GET 的 `/api/*` 校验 `Sec-Fetch-Site ∈ {same-origin, none}`（或要求自定义请求头），一次覆盖全部接口；③ 评估 `SameSite=Strict`。

#### P1-3 ✅ 账本分类以「名称」被引用，改名/删除不联动历史流水、预算、周期账单

- **位置**：`functions/api/txn-categories/[id].js:47`（rename 只更新分类行自身）、`:72-74`（remove 只按当前名归并流水）；引用方全部按名称存储且无外键：`transactions.category/sub_category`（`migrations/0001:68-69`）、`budgets.category`（`0003:12`）、`recurring.category`（`0003:24-25`）；聚合按名分组（`transactions.js:137-145,214-215`）。对照：**账户**改名是联动的（`txn-accounts/[id].js:37-41`），分类侧是遗漏。
- **触发**：把「餐饮」改名为「吃饭」→ 历史流水仍是「餐饮」→ 报表口径分裂；「餐饮」的月度预算 `used` 恒为 0（预算静默失效，用户以为没超支）；再删除「吃饭」→ 「餐饮」的流水成为无分类行的孤儿。
- **修复**：rename/remove 在同一 `env.DB.batch` 内联动 `transactions.category/sub_category`、`budgets.category`、`recurring.category/sub_category`（删除时同步删/迁移预算行）；长期改为按 id 引用。

#### P1-4 ✔ AI 新增待办复用残留「编辑态」，提交时覆盖既有待办（数据破坏）

- **位置**：`public/js/app.js:3459-3469`（`openTodoFromAi` 只 `f.reset()`，未重置编辑态）；对照 `app.js:2231/2241`（只有 `openTodoModal` 重置/设置 `todoEditingId`）、`app.js:5710`（提交按 `todoEditingId` 决定 POST/PUT）；服务端 `PUT /api/todos` 是全字段覆盖（`functions/api/todos.js:313`）。
- **触发**：同一页面会话内（PWA 不刷新很常见）：先「编辑」过某条待办（保存或取消都会留下 `todoEditingId`）→ 随手记被 AI 解析为待办（`detail=true` 很常见，`ai/parse.js:45`）→ 在弹出的待办弹窗点提交 → **旧待办被 AI 文本整体覆盖**（标题/日期/清单回落/优先级回落 P0/备注清空/星标取消，残留的重复规则与步骤草稿一并写入），而 AI 那条**不会新建**；弹窗标题仍是「编辑待办」，用户难以察觉。
- **根因**：`openTodoFromAi` 诞生于 v0.5.27（c2f19c2），`todoEditingId` 是 v0.5.53（3ff3264）引入，改造漏掉此入口。
- **修复**：`openTodoFromAi` 复用 `openTodoModal(null)` 后再预填；或开头显式重置 `todoEditingId/modalSteps/repeatDraft` 并刷新弹窗标题与按钮；提交成功后清空 `todoEditingId`。

#### P1-5 ✅ 「备份」只能导出、不能恢复——全站没有恢复导入功能

- **位置**：全仓库无 import/restore 端点（检索 `恢复|restore|导入备份` 仅命中注释）；前端唯一备份动作是 `exportAllData()`（`app.js:5220-5232`，blob 下载）。Worker 每日自动备份 14 份快照到 R2 `backup/d1/`（`worker/src/index.js` dailyBackup），同样没有从应用恢复的入口。
- **影响**：换设备/误清空/实例迁移时备份不可用，需手工 `wrangler d1 execute`；对主打「数据安全」的产品是核心缺口（清空数据页还要求「已备份」才能二次确认，见 `openClearModal`）。
- **修复**：见 §7 点子 1（恢复导入 + 快照一键回滚方案）。

### 3.3 P2（18 项）

---

#### P2-1 ✅ `/api/client-log` 公开且无限流：刷写配额 DoS + 日志污染

- **位置**：`functions/api/client-log.js`（公开接口，每请求 INSERT+DELETE 两次 D1 写）；中间件 PUBLIC 列表 `_middleware.js:5`。
- **影响**：匿名攻击者高频 POST 可耗尽 D1 每日写入配额（免费档约 10 万行/天），导致全天业务写入失败；`message/url/ua` 全部攻击者可控（有 500/200/200 截断），会污染系统信息页「最近错误」（展示侧已转义，无 XSS，见 §4）。
- **修复**：最低成本——在 Cloudflare 控制台给 `/api/client-log` 加 WAF 限流规则（免费版有 1 条额度）+ 把频率限制挪到 KV/D1 计数；或要求登录后才上报（登录页错误改走 console）。

#### P2-2 ✅ 「清空全部数据」副作用合集：R2 附件与备份镜像不清、推送订阅被清且不自愈、播种字典丢失、`kept` 不如实

- **位置**：`functions/api/data/clear.js:23,43` + `functions/api/data/_tables.js:34,42`；`worker/src/index.js`（backup 镜像永不删除）；`app.js:2655-2658`。
- **分解**：
  1. **R2 残留（隐私+存储）**✅：clear 只删 D1 行，不删 `BUCKET` 对象；且 Worker 每日备份把全部附件镜像到 `backup/files/` 且「镜像不删除」（设计如此，见 `dailyBackup` 注释）→ 用户以为清空了，照片/证件/视频仍在 R2 两处。清空数据后这些对象无任何 DB 引用，应用内不可达也无法清理。
  2. **推送订阅被清**📄：`push_subscriptions` 不在 EXCLUDE → 清空后 Worker 无订阅可推；浏览器本地订阅仍在但不会自动重报（只有点「开启通知」才 `subscribePush()`）→ 定时推送**静默失效**。
  3. **播种数据丢失**📄：迁移播种的词库（称谓/剂型/分类/位置）、账本默认分类、默认账户（含受保护的「人情往来」）、默认清单「生活」一并被清且不重放 → 药箱表单下拉变空（`medicine.js:302-307`）等。
  4. **响应 `kept` 只列 2 项**📄（实际还保留 `api_tokens/client_logs/d1_migrations`）。
- **外键专项结论（明确，可放心实施修复）**📄：把各表 DELETE 放进同一 batch **不会**出现外键约束失败，也**不会**在库内留下孤儿行——迁移中全部 17 条外键均为 `ON DELETE CASCADE/SET NULL`（B 报告 §4.5 有逐条表），D1 默认强制外键且 batch 是事务。
- **修复**：clear 改显式白名单；同步删除 R2 中 `rjgx/` 前缀对象 + 提供「彻底抹除」选项清 `backup/files/` 对应键；`push_subscriptions` 移入 EXCLUDE 或清空后强制重新订阅；播种 SQL 抽成可重放种子清单；`kept` 由排除名单推导。

#### P2-3 ✅ 农历生日在日历上被画到错误的公历日期（双处独立确认）

- **位置**：`functions/api/_profile.js:119,129-134,140-145`——`nextBirthdayOf` 农历分支算出了正确公历日 `nextMs`，但返回 `date: \`${nd.getUTCFullYear()}-${p2(M)}-${p2(D)}\``，M/D 是**农历**月日；`functions/api/contacts.js:12,20` 原样返回为 `nextBirthday`；消费方 `public/js/app.js:1255-1261` 以 `start: \`${c.nextBirthday} 00:00:00\`` 生成日历全天事件。
- **示例**：农历八月十五生日 → 接口返回 `2026-08-15`，日历把生日标在公历 8 月 15 日，实际 2026 年中秋是 9 月 25 日。同一响应的 `days`（按 nextMs 计算）是对的 → 出现「首页提示快过生了，日历上却不在那天」。
- **修复**：`date` 统一用 `nd` 格式化：`${nd.getUTCFullYear()}-${p2(nd.getUTCMonth()+1)}-${p2(nd.getUTCDate())}`。

#### P2-4 ✅ 推送 Worker：农历生日按公历近似推送 + 同一生日连推 8 天 + 已过期药品不再提醒 + 幂等标记写失败会每分钟重推

- **位置**：`worker/src/index.js` dailyJobs。
- **分解**：
  1. 农历生日直接拿农历月日当公历月日匹配（代码注释自认「近似策略…精确农历推送待 lunar 表引入」）——而 `functions/api/_profile.js` 里**已有**现成的 `toLunar`（约 60 行，覆盖 1900-2100），worker 是独立工程目录，把它复制/共享过去即可，近似推送可立即升级为精确。
  2. 生日扫描 `for (i = 0; i <= 7; i++)` → 同一生日连续 8 天各推一条（注释写的是「未来 1/3/7 天」）；建议改为仅 D-7/D-3/D-1/D0 各推一条。
  3. 药品提醒只扫 `[today, +30d]` 的临期窗口，`expiry < today` 的已过期药品**不再有任何提醒**（健康安全相关）；建议增加「已过期 N 件，请清理」。
  4. 每日任务幂等标记 `last_daily_run` 写入失败被 `catch(_){}` 吞掉 → 当天 06:00 后每分钟重跑 dailyJobs → 生日/药箱推送每分钟重发一次。建议标记写入失败时 `console.error` 并在本轮中止推送，或改为先写标记再推送。
- 另：`datetime('now','localtime')` 在 D1 上的实际时区未核实（待证项 §6-1），建议统一改 `datetime('now','+8 hours')` 或 JS 侧格式化。

#### P2-5 ✅ 安卓壳把管理员密码明文存 SharedPreferences，且允许系统备份

- **位置**：`android/.../MainActivity.java`（`PREF_PASS` 存默认 SharedPreferences；配置页 `etPass.setText(prefs.getString(PREF_PASS,""))`）；`android/app/src/main/AndroidManifest.xml`（`android:allowBackup="true"`）。

## 7. 点子方案（基于本次审计的功能发散）

### 点子 1：「真备份」——恢复导入 + 快照一键回滚（直接补 P1-5）

- **动机**：现在导出 JSON 无人能吃回去，R2 里还躺着 14 份每日快照同样没法用；「清空重建」按钮比「恢复」还显眼，是产品最拧巴的一处。
- **方案**：
  1. `POST /api/data/restore`：上传备份 JSON → 先落一张 `restore_jobs` 临时表做**结构校验与预览**（按表统计将写入/覆盖行数、缺失表、版本差异），二次确认后在一个 `env.DB.batch` 事务内清空并重放；`app_settings` 只恢复白名单键；附件类提示「请用 R2 镜像恢复脚本」。
  2. 「数据安全」页列出 R2 `backup/d1/` 的 14 份快照（`BUCKET.list`），一键「预览→回滚到某天」；回滚前自动先把当前库导出一份到 `backup/d1/pre-rollback-<ts>.json`。
  3. 恢复完成后强制所有设备重新登录并清前端缓存（防串号）。
- **工作量**：后端 2 个端点 + 前端一个页面，约 1-2 天。这是审计发现里「性价比最高」的新功能。

### 点子 2：安卓壳原生能力桥——让 APP 补齐 Web 做不到的三件事

- **动机**：WebView 没有 Push API（推送在 APP 内天然失效，现在只能靠手动闹钟深链）；P2-6 的下载问题也无解。
- **方案**：`addJavascriptInterface(new SzshBridge(), "SzshAndroid")`（`@JavascriptInterface` 仅暴露 4 个方法，页面侧已有 `isAndroidShell` 探测点）：
  1. `download(url, filename)`：桥内用 OkHttp 带 Cookie 下载到 Downloads（解决附件/备份导出）；
  2. `notify(title, body, deeplink)` + 壳内 **WorkManager 每 15 分钟**调新增的 `GET /api/push/pending`（Worker 算好到期事项写一张 pending 表，带已推送去重键）→ 系统通知，点通知 `loadUrl(deeplink)`（解决 APP 内无推送）；
  3. `setAlarm(title, hh, mm)`（替代现在脆弱的 `intent://` 拼接）；
  4. `biometricUnlock()`：启动时用 BiometricPrompt 保护已登录态。
- **工作量**：壳侧约 300 行 + 后端一个只读端点，1-2 天；顺带把 P2-5 的明文密码存储一并重构掉。

### 点子 3：「数据健康巡检」页——把审计发现变成常驻自检

- **动机**：本次审计的多数数据完整性问题（孤儿分类、幽灵账户、非法日期、重复待办实例、漂移的周期账单、R2 孤儿对象）都可以程序化检出。
- **方案**：`GET /api/data/health` 返回问题清单：① `transactions.category` 不在 `txn_categories` 的名称及流水数；② 不在 `txn_accounts` 的账户名；③ 不满足日历有效性的日期（transactions/todos/events/recurring/medicines）；④ 同标题同日期的重复待办实例；⑤ `recurring.next_date` 的「日」与创建时不符（漂移检测）；⑥ R2 中无 DB 引用的 `rjgx/` 对象（`BUCKET.list` 对账）。前端巡检页逐项显示「发现 N 处 → 一键修复」（修复端点复用 P1-3 的联动逻辑）。可在「系统信息」页常驻一张健康卡片。
- **工作量**：1 天左右；它同时是 P2-14/P2-15/P2-16 修复后的回归验证工具。

### 点子 4：AI 周报/月报——让已配置的大模型干第二件活

- **动机**：AI 目前只有随手记解析一个用途；`review.js` 已有现成统计数据，万事俱备。
- **方案**：`POST /api/ai/summary`：把本周/本月的结构化统计（支出分类占比与环比、预算达成、待办完成率、习惯连续度、临近生日与久未联系名单、药品临期）喂给默认模型，生成 300 字自然语言周报 + 3 条建议（如「餐饮比上月高 40%，主要来自周五外卖」「王老师生日还有 3 天」）；数据全部本地统计后只发摘要数字，隐私政策里补一条披露。首页顶部可折叠展示，MCP 加一个 `weekly_summary` 工具。
- **工作量**：1 天；注意沿用 `aiSuggested` 式标注（本次审计恰好发现药典 AI 判断未标注的教训，B-P3-05）。

### 点子 5：时区自愈——为「海外可用的国内习惯 App」收尾

- **动机**：P2-13 是海外使用体验的最大硬伤，且 v0.5.48 已改了一半（前端本地、后端仍 UTC+8），现状是两头不一致。
- **方案**：登录后前端上报 `IANA 时区`（`Intl.DateTimeFormat().resolvedOptions().timeZone`）存 `app_settings`；`_lib.js` 的 `todayStr()` 接受按该时区计算的「今天」并统一贯穿 todos/transactions/recurring/budgets/period；Worker 的推送与日检按同一时区换算（每分钟 Cron 里多一次查表）。关键规则：**录入时刻**用本地时区，**生日期间的显示**可保持北京口径可选。
- **工作量**：1 天；配一组纯函数单测（时区是回归重灾区）。

### 点子 6：通知瘦身 + 生日提醒节奏化

- **动机**：P2-4 的「连推 8 天」与锁屏明文。
- **方案**：生日推送改为 D-7/D-3/D-1/D0 各一条（文案带「农历八月初二 · 公历 9 月 23 日」双口径，换算复用点子 5 修好的 toLunar）；`app_settings` 增加「通知隐私模式」：推送 payload 只带计数（「有 3 项待办，1 项已逾期」），正文细节点击后拉取——payload 本身是端到端加密的（RFC 8291），但锁屏可见文本默认带敏感词（药名/人名/待办标题）。
- **工作量**：半天。
